## Public API

- `stade_tangent/adjoint/hvp_file(in_path::String, out_path::String; ...)`: writes to `out_path` a Julia source result of differentiation by STADE of the (multi-)kernel file at `in_path`. In the multi-kernel case, inlining is performed in the kernel which is not called by any other one in the file (named root kernel). The inlined root kernel is the one subject to differentiation.

  `stade_adjoint` and `stade_adjoint_file` take `primal_outputs::Bool = true`. With `false` the generated adjoint does not update the primal outputs of the kernel: it drops the forward sweep when the backward sweep does not read what the forward sweep writes (a linear update, such as a stencil step), and the stores into arrays that nothing in the adjoint reads. The arrays that the kernel writes then keep their input values, and the gradients are identical. A kernel with nothing to drop is generated as with `true` (the `_file` form prints a note). A store is kept when it reads a scalar that an inner loop accumulates beside an adjoint increment (the output layer of a perceptron): that sum is what lets the GPU stage split the gradient loop, and dropping it made the adjoint 2 to 3 times slower. On the GPU the result is usually faster (1.1 to 1.7 times on the stencil, scatter and solver kernels of the benchmark set). Time both settings.

  `stade_adjoint_split(expr; independents, dependents)` returns the adjoint as two functions: `NAME_b_fwd` re-runs the primal and records the tape, and `NAME_b_bwd` only reads the tape and runs the reverse sweep. A caller that needs many reverse sweeps at one primal state (the adjoint of a fixed-point iteration) records once and replays the backward function. The result is `(initstacks, forward, backward, carry_init, carry_f, carry_i, restore, consume)`: `restore` lists the primal arrays and `consume` the host stacks that the backward function rewrites or pops, so a repeated sweep needs a fresh copy of each; `carry_*` move the scalars that cross from one half to the other. It uses `keep_push_pop = false` and no loop fusion. There is no HVP split. The JACC code of both halves matches the CPU full adjoint on a V100 (357 of 362 corpus kernels; the other rows fail for the full adjoint too); a kernel with a host stack in `consume` has no device form. The manual (IV.11) has the contract.

  `stade_adjoint` and `stade_adjoint_file` (the file entry calls the in-memory one) give a kernel with counted loops with a guard (`for kk = 1:maxit` holding one `if residual > tol`, a solve loop) a fixed-point adjoint when it can: the solve loop may sit at the top level or inside loops and branches at any depth (a time loop that solves at each step), and a kernel may hold several, and there is no other function to call. The path applies with `keep_push_pop = false`, `fuse_ii_loops = false` and `primal_outputs = true`, to a loop whose features all appear in a validated corpus kernel (no division by a value computed from a reduction, nesting depth 2 at most, no `if` inside the guard, a symbolic tolerance, calls from `div`, `mod`, `sin`, `cos`, `tanh`). STADE prints one `@info` line each time: the reason when it keeps the unrolled adjoint (any other kernel or flag), or a note when it takes the fixed-point reverse. The default flags give the same output as before. The forward pass keeps one slot of tape per instance of a solve loop (one execution of it, at one point of its enclosing loops), the last active iteration's, so the tape does not grow with the cap (a 1e6-point array state: 7.45 GiB with the cap-sized tape for `maxit = 1000`, 7.6 MiB now; the 3-level multigrid kernel: 684 MiB, 6.8 MiB). An enclosing loop whose iterations are independent is refused (a GPU stage offloads such a loop and a sweep cannot run in a thread), and so is a state that a statement reads, with its value needed by the adjoint, before a solve loop overwrites it (the reverse leaves the state at the last iteration's value, not at the value the loop found on entry). A solve loop that stopped on its cap `maxit` in any instance has no fixed point, so the adjoint raises an error that says so (raise the cap or the tolerance, or use `keep_push_pop = true` for the derivative of the iterations that ran); a loop with `maxit = 0` runs no iteration and raises nothing. A loop that converged repeats the reverse of the last active iteration until the state adjoint settles, with the loop's own `tol` as the stop rule. If the sweeps do not settle, the adjoint raises an error (on CPU inside the adjoint, on a device from the host: one host read of `fp_info[5]`, which says which of the two errors it is). Because the adjoint reads one slot only, a loop whose body reads its own cap `maxit` is refused. After a converged loop the arrays hold the converged field, not the entry values. `stade_hvp` takes the same path (one slot of tape, sweeps that stop on the state adjoint and its tangent; the HVP tape of a time loop with a cap of 2000 is 57 elements where the unrolled one is 54048); the tangent differentiates the iterations that ran, so it agrees with this adjoint only to the loop tolerance. The validators (`stade_validate_*`) check the unrolled adjoint and say so with one `@info` line, because the derivative of the limit differs from the loop as executed by about the loop tolerance, which their random baselines do not hold tight; `test/validate_fixedpoint.jl` checks the fixed-point adjoint at a tight tolerance. `test/validate_fixedpoint_fuzz.jl` runs generated kernels (random statements around random solve loops) through the dispatch: an accepted kernel must match a finite difference; of the kernels refused for the entry value, 19 % would have been right (the rule is conservative; none of 620 accepted kernels was wrong). With one solve per step of a time loop the tape is 2 state arrays per step (15.3 MiB per step at 10^6 points, 149 GiB at 10^4 steps), not `maxit` times that (the last iteration's slot is not stored: the reverse starts from the converged state, so the gradient differs from the cap-sized tape by about the square root of the last residual, 1e-11 at `tol = 1e-24`); a longer time loop needs checkpointing in time, which is not built. `agen_adjoint_unrolled` returns the unrolled adjoint for a test that needs it. The manual (IV.11) has the detection, the whitelist, the stop rule and the limits.

  `stade_adjoint` and `stade_adjoint_file` take `checkpoint::Bool = false`. With `true` a sequential loop at the top level of the kernel that holds tape (a time loop: `for t = 1:nt`, each step reads what the one before wrote) is a checkpointed region. The forward pass saves the state at the start of each segment of `ck` steps, and the reverse pass restores one checkpoint, runs the segment again with its tape and reverses it, so the tape holds `ck` steps and not `nt`. The adjoint and `initstacks_NAME_b` take `ck` (the segment length, at least 1) as one more argument, and the kernel takes it as its last argument, so the generated primal beside the adjoint is the strip-mined kernel. The shadows and the returned scalars equal those of the adjoint without checkpoints bit for bit (`test/validate_checkpoint.jl`: 22 kernel shapes, 0 to 10 steps, `ck` from 1 to more than `nt`; `test/validate_checkpoint_corpus.jl` forces a region on every sequential loop of the corpora: 139 kernels, none differs). For `nt = 10` and a 6-point array the tape is 60 elements without checkpoints and 14 with `ck = 2`, and the tape of a segment does not depend on `nt`; the cost is one more forward run of every step. The checkpointed path applies with `keep_push_pop = false` and `fuse_ii_loops = false`; STADE prints one `@info` line with the reason for every loop that is not a region (independent iterations, no tape, a bound that changes inside the loop, a literal trip count of 8 or less) and for a flag that is not supported, and keeps the adjoint without checkpoints. The device code (`stade_gpu` for CUDA, `stade_jacc`) takes the checkpointed adjoint and its `initstacks_*` as they are; on a V100 (10^6 points, 100 steps) the stacks of `phc_heat_steps` shrink from 1526 MiB to 244 MiB at `ck` = 10, at 1.9 times the time, with the same shadows bit for bit. `stade_hvp` takes the same `checkpoint::Bool = false`: the HVP saves the tangents beside the state and gives the same results as the HVP without checkpoints bit for bit (`test/validate_checkpoint_hvp.jl`, 344 checks; the forced corpus, 139 kernels). On a V100 (10^6 points, 100 steps, `phc_heat_steps`) the HVP tape is 3.0 GiB without checkpoints (1526 MiB of stacks and 1533 MiB that the HVP allocates for the shadow tape) and 0.5 GiB at `ck` = 10 (336 MiB and 153 MiB), at 1.41 times the time, with the same results bit for bit; 2500 steps fit at `ck` = 50 (2.3 GiB of tape). A region may hold solve loops (a time loop that solves at each step) or follow one: the kernel keeps its fixed-point reverse, each step's solve keeps its one-slot tape, and the checkpointed adjoint gives the same shadows, returned scalars and `fp_info` as the fixed-point adjoint without checkpoints bit for bit (`test/validate_checkpoint_fp.jl`: every fixed-point shape with a region forced, in the converged, zero, cap and no-cap regimes, 144 checks). A solve loop that the fixed-point reverse refuses keeps the adjoint without checkpoints. An array that every step overwrites before it reads it (a scratch array: the Jacobi buffers of a time step that solves) is not saved by a segment. The state of a region is every array and every float scalar it writes, the integer scalars that hold a value on entry, and the arrays and scalars that it reads and a later statement writes (the segment runs again after that statement, so these are saved once before the region and put back for its reverse). It is larger than needed and safe. A kernel that STADE cannot size or rewrite (a ragged tape, 17 of 139 forced corpus kernels) keeps the adjoint without checkpoints and says why. A variable that the reverse sweep never restores (an accumulator such as `loss[1] = loss[1] + ...`) keeps its forward value, as in the adjoint without checkpoints. An array that the reverse restores at some statements and leaves at others ends at the state after the first segment, where the adjoint without checkpoints leaves the accumulated elements at their forward values; the shadows are exact. The default is the adjoint as before, byte for byte.

- `stade_cuda/amdgpu/metal/jacc_file(in_path::String, out_path::String; ...)`: writes to `out_path` a Julia source result of GPU porting by STADE of the (multi-)kernel file at `in_path`.

  A `while` inside an independent loop (a per-element solver: Newton, bisection, a fixed point) runs sequentially inside each device thread, in the primal and the tangent. The loop is offloaded when every scalar it uses is private to the iteration and every array access is owned by the iteration, the same proof as for an inner `for`, applied to the condition too. A `while` that does not terminate hangs the kernel as it would hang the host; STADE does not add an iteration cap, because that would change the result. Threads of one warp that leave the `while` at different iterations make the warp wait for the slowest one. The adjoint and the HVP of a `while` are still refused with `keep_push_pop = false`.
  To get the adjoint or the HVP of such a solver on the GPU today, write the `while` as a counted loop with a guard: `for k = 1:maxit`, then `if st > tol` around the body. This is a supported form with `keep_push_pop = false`. The tape has a closed-form size of `n * maxit` slots per stack, so it is sized by the cap and not by the real trip count (100000 elements with a cap of 50 and 5 stacks is about 200 MB). The backward sweep runs `maxit` iterations per element. Ten kernels in `test/counted-corpus/` show the form (the four element-wise ones and six grid solvers: Jacobi, Gauss-Seidel, power iteration, conjugate gradient, heat steps, multigrid), and `validate_counted_while.jl` and `validate_counted_physics.jl` check them. They agree with the `while` version to the last digit on the CPU, including `phc_mg_solve` (the multigrid nest has stacks that fall back to `push!`/`pop!`; `validate_tainted_stacks.jl` checks that case). On the V100, `phc_mg_solve` runs on CUDA and JACC and agrees with the CPU (adjoint and HVP), but its control flow stays on the host, so it is far slower than the CPU (43 to 85 s against 0.02 to 0.045 s at 4095 points and 12 levels).

  Two rules decide whether the counted form runs on the device (measured on a V100, 20000 elements):
  - Assign the guard scalar outside the guard. Compute the step every pass, apply it inside `if st > tol`, then set `st = abs(step)` after it (see `phc_kepler_newton`). A scalar assigned only inside the guard keeps the adjoint of the element loop on the host: 63 s against 0.02 s on the CPU for 20000 Newton solves. With the rule, kepler, colebrook and react run the adjoint in 0.15 to 0.5 ms against 20 to 40 ms on the CPU.
  - Do not store a trip counter in an output array. It makes the array active and forces an integer stack, which `keep_push_pop = false` refuses. A counted kernel reports no trip count.

  A solver that carries a value between sweeps (Gauss-Seidel, conjugate gradient, power iteration, heat steps) gets the closed-form tape but stays on the host, and is slower than the CPU on the V100 (9 to 37 s against 0.012 s). The same holds for the HVP of the bisection kernel.

  Level nests (multigrid): with `keep_push_pop = false`, a loop bound assigned inside a loop that sits inside another loop with changing bounds (`n = nl - 1` in a level loop, the level loop inside a cycle loop) keeps host `push!`/`pop!` stacks, because the tables for ragged bounds cover one nesting level. On a GPU each stored value then costs a copy: `phc_mg_solve`, 33 cycles, 4 levels, V100, adjoint 2,192 ms (117,383 launches, 142,695 copies). `stade_adjoint_file` and `stade_hvp_file` print a note when the generated function has such calls. If the bound keeps its value from one pass to the next (`n = nfine - 1`), assign it once before the loops: no stacks (`test/validate_host_stack_note.jl`, the same assignment moved out of the level loop gives no note). If it changes (`nl` halving per level), write the inner loops with a constant bound (the finest size) and wrap each body in `if X <= bound ... end`: same primal, no stacks, 41 ms (53 times faster; the arrays must be allocated at the finest size, and the tape grows from 0.03 to 2.1 MB). Corpus census (`test/census_tainted_stacks.jl`, 331 kernels that `keep_push_pop = false` accepts): 21 have a ragged bound, 20 of them resolve into closed-form tables, `phc_mg_solve` is the one that keeps host stacks.

  Known limit: with the default `fuse_ii_loops = false`, an independent loop that rewrites a local scalar (`t = x[i] * x[i]; t = t + 1.0; y[i] = sqrt(t)`) keeps a snapshot stack for that scalar in the adjoint and the HVP. The stack carries a value from one iteration to the next, so the forward and the reverse loops stay on the host. The result is correct and slower. With `fuse_ii_loops = true` STADE proves the stack unnecessary and offloads the loop, so pass `fuse_ii_loops = true` for a GPU target (the generated and validated modes agree; see `test/validate_scalar_stack_limit.jl`). In the 111 battle subjects this is the only shape on which the two settings differ.

  A loop whose whole body is one scalar accumulation gets BOTH lowerings and a run-time test on its own trip count: below `reduction_threshold` iterations it runs the loop as it stands, as an atomic kernel when the accumulator is an array element and as a host loop when it is a local scalar; at or above the threshold it evaluates `target = target + mapreduce(f, +, view(a, lo:step:hi), ...)`. Neither wins everywhere. A tree reduction pays a fixed multi-pass cost a short loop cannot amortise, and an atomic on one address serialises its threads. On an NVIDIA A30, best-of-5 after warmup, `dotprod`'s adjoint crosses over near 24000: atomic 11.72 vs mapreduce 71.59 us at n=1024, 62.25 vs 72.12 us at n=16384, 876.21 vs 85.36 us at n=262144.

  The JACC backend applies the same test, choosing between its atomic kernel and `JACC.@parallel_reduce`. Measured on a Tesla V100, its crossover sits near 65000: atomic 735.31 vs reduce 1043.96 us at n=1024, 780.64 vs 726.00 us at n=65536, 1592.85 vs 641.37 us at n=262144. One shared default is used rather than one per backend, because that number and CUDA's bracket it.

  The same test governs a reduction into a local scalar, where the alternative is a host loop rather than an atomic kernel. An earlier version lowered that case unconditionally, on the reasoning that a device reduction must beat a host loop reading one scalar per element. Three consecutive same-process comparisons on a V100 at n = 16 say otherwise: the host loop at 1600.9, 1599.1 and 1524.6 us against 1820.5, 1872.0 and 1668.0 us.

  The arrays the accumulation reads may be indexed three ways (v0.5.11): by the loop variable plus an invariant offset (`x[i]`, `x[i + 1]`, `x[i - k]`), by the loop variable in one dimension and an invariant index in the others (`r[i, 1]`), or, in a flattened 2D nest `for i = 1:K * M`, by `div(i - 1, M) + a` and `mod(i - 1, M) + b` (the same `M` in both, rows first). Every read in the term must use one of these forms and all must be the same kind. Anything else (a stride `x[2 * i]`, a diagonal `x[i, i]`, a term that reads its own accumulator, a bare use of the loop variable) leaves the loop on the host. A loop that also writes an array cannot hold a local sum: put the sum in a loop of its own.

  A LOCAL scalar accumulator has no atomic kernel to fall back on, so below the threshold it runs as a host loop that reads each device array element by element, about 10 us per read on a Tesla V100. It therefore switches to the device reduction at 16 iterations, not at `reduction_threshold`: it uses the smaller of the two. Measured on a V100 (seconds): conjugate gradient on 32 x 32 points, 6.28 with the old single threshold and 0.015 now; power iteration at n = 256, 29.4 and 0.36; Jacobi on 32 x 32 points hit the job time limit and now takes 0.24. An array-element accumulator keeps `reduction_threshold` (32768). `reduction_threshold = 0` puts every reduction on the device.

  `reduction_threshold` defaults to 32768, chosen to avoid a regression rather than to capture every win. The same benchmark on a Tesla V100 does not reproduce: two identical runs gave 1160.74 us and 88.60 us for the reduction at n=262144, a 13x swing, while the atomic timings agreed within a few percent. No threshold can be fitted to that, so the default sits above the crossover of the one measurement that was stable. Measure your own hardware and lower it if that is worth doing. The view matches the loop's own range, so a loop that does not start at 1 reduces only the elements it visited, and an explicit `init` keeps a zero-trip loop contributing zero. `keep_all_atomic` was removed in v0.3.0. It selected between the two lowerings at generation time, which the run-time test now does per call; its two settings are reachable as `reduction_threshold = 0` and as any value above every trip count.

  Two CUDA-only keywords, both on by default, change how a reduction is lowered; `warp_atomics = false` and `sync_free_reduce = false` restore the previous output exactly. `warp_atomics`: an array-element atomic add `A[i] += v` becomes a call to a generated helper that, when all 32 lanes of the warp are active and agree on the index, adds the 32 values with a shuffle tree and lets lane 0 issue one atomic; in every other case it issues the plain atomic. The helper assumes one-dimensional thread blocks, which the generated launches use. It changes the order of the float summation, so results differ from the plain atomics in the last bits, and an accumulation into a single address (a loss) is much cheaper. `sync_free_reduce`: the large-trip branch of an array-element reduction becomes a device-side broadcast add into a one-element view (`view(A, i:i) .= op.(view(A, i:i), reduce(...; dims = 1))`) instead of a host `@allowscalar` assignment. That branch no longer copies a scalar to the host, so the host does not wait in the middle of the call sequence. AMDGPU, Metal and JACC output are unchanged. A CUDA graph cannot capture that large-trip branch: the dimension-wise reduction of CUDA.jl fails during capture, and the previous host form fails there too. To capture the whole adjoint call, pass `reduction_threshold = typemax(Int)`. Every reduction then uses the atomic kernel, which `warp_atomics` makes cheap. On a Tesla V100 with the U-Net adjoint, this setting gave the same step time as the default and a graph launch about 1% faster; the benefit is a lower launch cost per step, not a faster device.
  JACC kernels with more than 32 free variables take them as one tuple (`__jargs`) and unpack it on the device. JACC splats the launch arguments into the kernel, and Julia cannot compile a splat of more than 32 values on the device. Kernels with 32 or fewer free variables are unchanged. This lets a loop with a very wide body, such as the `ttgc` HVP cell loop (42 free variables), run on the device instead of staying on the host.

  CUDA only, opt-in: `fresh_gradient = true` writes a gradient element instead of accumulating into it (`g[i] = e` for `g[i] = g[i] + e`) when the adjoint array provably gets one write per element per call. It saves one read pass over the array, which is bandwidth-bound in a dense layer (on a V100 the gap of `mlp3` at 79M parameters to JAX goes from 1.41 to 1.12). The caller must pass the gradient arrays zeroed and make one adjoint call per reset; the CPU adjoint still accumulates, so the two contracts differ for a flagged array. A caller that breaks the contract gets wrong gradients and no error. `fresh_check = true` (default `false`, needs `fresh_gradient`) makes the generated host function raise an error at entry if a flagged gradient array holds a non-zero value or a NaN, which catches a missing reset and a second call without a reset. It costs one reduction and one synchronization per flagged array per call, so use it for testing and turn it off for timing. The header of the generated file lists the flagged arrays.
  CUDA only: `split_coalesce` (default `true`) gives the split-reduction twin a coalesced layout when its lane loops are unit-stride (transformer adjoint d2048, V100: 82.9 to 77.0 ms). CUDA only: `cublas = W` (default `2^26` from v0.4.62; `0` turns it off) runs an adjoint product as one `CUDA.CUBLAS.gemm!` when M * N * K >= W (same kernel, d2048: 76.9 to 62.3 ms; W = 2^28 is a safe value). With `cublas > 0` the scratch of a gemm product is an uninitialized array (beta = 0) and the seed scratch of an adjoint is not zeroed (d2048: 62.3 to 61.6 ms). The split twin is now also built for the adjoint of a loop with an empty loop or a reused temporary (`ufv_gather_step`; opt-in `split_reduce = 8, split_min_inner = 4, split_max_out = 10^8`: 1e6 cells 1.88 to 1.35 ms; slower for `mlp3` and `mpnn_gather`, so per kernel). CUDA only, opt-in: `row_block = M` (default `0`) adds a row-block twin for a flat loop `for idx = 1:R*N` with `i = div(idx - 1, N) + 1`, `j = mod(idx - 1, N) + 1` and an accumulation into `A[i]` (one block per row, one add per row instead of one per warp); the host launches it when `N >= M`, the range is whole rows and there are at least 64 rows (mlp3_push adjoint, 79M weights, V100: 3.11 to 2.61 ms). CUDA and Float64 only: `serial_loops` (default `true` from v0.5.26; `false` gives the generated code of v0.5.25, checked over the whole corpus) runs an order-dependent host loop that holds no parallel loop in one device thread (`cuda_serial_*!`, `threads = 1 blocks = 1`): scalars go in by value and the scalars the host reads afterwards come back in one box with one copy. A loop with a stack operation, a boxed scalar or a kernel inside stays on the host. Same draws on the V100, corpus kernels with a host loop: small draw 367 to 146 ms in total (159 kernels, none slower), the 52 kernels that launched no device kernel 79 to 3 ms; large draw, the 28 heaviest, 39.7 s to 2.0 s (`so_liveout` 24.6 s to 32 ms). Adjoint and HVP match the CPU on the V100. JACC, AMDGPU and Metal have no serial track. CUDA and Float64 only: `glue_kernels` (default `true` from v0.5.26; `false` gives the code of the serial track alone, checked over the whole corpus: 4,400 plans, 0 differ) runs the scalar statements between the kernels of a host loop (the `CUDA.@allowscalar` blocks) as one-thread kernels (`cuda_glue_*!`, launched like any other kernel, no copy), and a Float64 scalar that only kernels and other glue read (`alpha = rs[1] / s[1]`) lives in a one-element device box. A scalar the host itself reads (an `if`, a bound, an index) stays on the host. Same draws on the V100 (serial track on in both, 159 kernels, adjoint and HVP, 318 runs, parity ok on all): sum of wall time 2247 to 253 ms in the first job, the CG kernels `pv_a11` and `pv_a12` about 2.5 to 3.5 times faster (HVP 3.8 to 1.5 ms), `transformer` HVP 80 to 28 ms; `remat_shapes` is about 15% slower (cheap host writes became launches). JACC has the same pass: `stade_jacc(...; glue_kernels = true)` (default `true` from v0.5.26, with `jacc_async = true` below; `glue_kernels = false` is the rollback; glue kernels are `jacc_glue_*!(__jacc_i, ...)`, launched `JACC.@parallel_for range = 1`, boxes are `JACC.array([0.0])`; Float64 only). `br_cg1d2` adjoint on the V100, µs per outer iteration at n <= 4096: 609 without, 518 with glue (-15%), 585 with `jacc_async = true`, 402 with both (-34%); the primal is about 10% slower with glue and synchronous launches (190 against 173), 8% faster with `jacc_async = true`; glue alone makes the primal slower, so the two defaults go together. A JACC launch costs several times a CUDA one, so the gain is smaller than on CUDA (131 µs there). The five solver-shaped kernels on JACC (adjoint and HVP, 18 to 1026 points per side, 40 cases): glue alone gives 0.81 to 1.32 times (20 cases slower), with `jacc_async = true` in both 0.88 to 1.68 times (6 cases slower, the worst 0.88); glue plus async against the defaults is 1.05 to 1.76 times. Two runs with glue off differ by as much as glue on against off (up to 1e-10 at 18 points, atomic order). `jacc_async = true` (default from v0.5.26) is audited: the host forms of 331 corpus plans (reads, writes, copies, frees, reductions) were each tried on a V100 right after a long asynchronous launch, JACC 1.3.1, and the glue-and-async parity on the V100 matched the synchronous result on 122 rows and on 36 same-draw runs. With `jacc_async = true` every launch inside the generated function is asynchronous and the function waits once, before each of its returns (`jacc_async_wait = true`, the default), so its caller sees finished kernels. A kernel that returns `nothing` after a 12 to 44 ms launch returned after 0.02 ms without that wait and when the kernel ended with it; on the five solver kernels below (adjoint and HVP, 40 rows) the wait cost nothing measurable, and the 26 pinned large-draw corpus kernels matched the CPU on all 52 JACC rows. `jacc_async_wait = false` gives the earlier behavior: the function returns before its last kernel ends, and a caller that times it, sends a device buffer or reads it from another stream waits first. `test/validate_jacc_async.jl` fails on a host form that is not on the audited list. Defaults on from v0.5.26 (`stade_jacc`, `stade_jacc_file`, `stade_validate_jacc_file`): `jacc_async = true` and `glue_kernels = true`; `jacc_async = false` and `glue_kernels = false` give the earlier code, and `jacc_async_wait = false` keeps the asynchronous launches without the exit wait. The exit wait calls `JACC.synchronize()`. The wait sits on the returns only, so a function that throws after a launch does not wait: the exception reaches the caller while the queued kernels keep running. On a V100 (JACC.jl 1.3.1, 20 launches of 29 ms, 5 trials per case) the exception arrived after 0.4 ms against 528 ms for the queue, and a read of the array right after it, from the same task or from another task, returned the finished result every time (10 of 10, equal to a synchronous run). A `finally` wait made the exception arrive after 528 ms and changed no result. So a host reader needs no drain; only a caller that times the failure, or hands a device buffer to a stream the host does not synchronize, sees the difference. Run on a V100 with JACC.jl 1.3.1 (every figure here) and, for a subset, JACC.jl 1.4.0 with CUDA.jl 6.3.1 (18 corpus kernels, adjoint and HVP, default flags, small draw, same driver): 32 of 36 rows match the CPU; the other four are the known `idm_dup_write` difference and the `phc_gs1d` draw with no signal; worst relative error 1.8e-12 (`unet` HVP, tolerance 9.5e-12); `phc_saha_bisect` (the 35-variable glue kernel), `br_cg1d2`, `pv_a11` to `pv_a13`, `transformer` and `ttgc` included. JACC.jl 1.5.1 (the release tree, in a temporary environment and a temporary Julia depot) ran the same 18 kernels with the same result, then the 75 corpus kernels whose generated code uses `@parallel_reduce`, `JACC.shared` or `launch_spec` (the parts of JACC.jl 1.5.1 that changed most): 148 of 150 rows match the CPU, the other two are the `phc_gs1d` draw with no signal, and 148 of the 150 error values are bit-identical to a paired JACC.jl 1.3.1 run (the two that differ are `unet`, which uses atomics; worst 1.0e-12). A compute node can install a JACC.jl version into a temporary environment, so another version can be run the same way. Other JACC.jl versions are checked by source only: by the JACC.jl source (not STADE versions), `JACC.synchronize` is defined in every JACC.jl tag from v0.4.0 to v1.4.0 and in the threads, CUDA, AMDGPU, Metal and oneAPI backends of JACC.jl v1.4.0, and the launch macro of JACC.jl v1.4.0 takes `sync`. V100, JACC 1.3.1, default flags, adjoint and HVP, small draw, BigFloat truth on a miss: 564 rows (282 kernels of seven corpora) match the CPU, every row changed elements, worst relative error 5.1e-13 (`unet` HVP, tolerance 9.5e-12). Also measured on the same GPU, CUDA and JACC, adjoint and HVP: the 45 `f3_nest_*` kernels (arrays of rank 3 to 6; 180 rows, all ok, worst relative error 1.1e-14) and `phc_colebrook` (4 rows, worst 7.9e-16, drawn with `float_range`). A baseline yaml stores an array of rank 3 or more as `shape: [..]` plus `data: [..]` in column-major order. `float_range = Dict(:re => (1e4, 1e6))` (to `stade_generate_baseline_file`, `val_generate_baseline` and `validate_corpus_gpu`) draws the named float arguments uniformly from that range, for a kernel that takes a `log10` or `sqrt` of an input that must keep one sign. `phc_gs1d` is vacuous at this draw (covered with pinned draws in the async audit). `idm_dup_write` and `f9_gather_write` differ from the CPU by design (a plain write through a gathered index that is not a permutation); they differ in the same way on CUDA and with both JACC flags off. A glue kernel with more than 32 free variables takes them in one tuple, as a loop kernel does (`phc_saha_bisect` HVP, 35: JACC's splat compiled to a dynamic call that the V100 refused). Solver-shaped kernels on the V100 with glue on (CUDA adjoint, µs per outer iteration, glue off to on): a 2D CG with the Laplacian as matvec goes 466 to 135 at 324 points, 514 to 135 at 66k, 680 to 287 at 264k and 1287 to 994 at 1M; a 2D Jacobi with an update-norm stop 90 to 61, 106 to 76, 208 to 175 and 566 to 536. Glue saves a fixed amount per iteration, so the gain fades once the kernels dominate. AMDGPU and Metal have no glue pass.

- `stade_ddp_file(in_path::String, out_path::String; per_sample, mode, reduced = Symbol[])`: writes to `out_path` a Julia source epilogue that runs the kernel at `in_path` data-parallel over a mini-batch with GPU-aware MPI, the pattern of PyTorch DistributedDataParallel. The kernel needs no batch loop and no rewriting: sample `s` goes to rank `mod(s - 1, P)`, every rank runs the kernel unchanged on its own samples, and the epilogue sums the parameter gradients across ranks. It differs from DistributedDataParallel in three ways: the gradients are summed, not averaged, so a 1/N factor belongs in the loss or the seed; the replicated parameters are a contract (the `:shared` buffers must hold the same values on every rank) and are not broadcast; and the Allreduce runs after the adjoint, without overlap. The stage does not batch a kernel: it only reduces the gradients. `per_sample` names the read-only arrays whose values change from one sample to the next; every other read-only array is treated as replicated. The generated file carries the derived role of every buffer as a comment, so the communication plan is auditable without re-running STADE.

## Wishlist 💡

- [x] ✅ [v0.2.2] Wrap common subexpressions into auxiliary variables
- [x] ✅ [v0.2.4] Add `ddpgen_` stage for data-parallel mini-batch execution code via GPU-aware MPI\
  Called `bgen_` until v0.5.0, with the public functions `stade_batch` and `stade_batch_file`, now `stade_ddp` and `stade_ddp_file`. The old names were misleading: the stage does not batch a kernel. Every rank runs the unmodified kernel on its own samples and the gradients are summed across ranks, the pattern of PyTorch DistributedDataParallel. The old names are gone, with no wrappers.
- [x] ✅ [v0.4.0] Add support to `:while` statement\
  Fixed in v0.4.3: activity did not propagate into a `while` body, so a body local was treated as passive at every use and the tangent came out silently zero. Any kernel whose `while` body assigns a scalar that then feeds an array must be regenerated.\
  The forward sweep records each loop's trip count and the backward sweep replays it as a `for`. The forward sweep still contains the `while`, since it has to run the loop to learn the count. The gradient is therefore taken at a fixed trip count, which is correct almost everywhere and wrong where the count jumps. A `while` runs on the host and needs `keep_push_pop = true`, since no launch can size itself around an unknown trip count and that mode has no closed-form stack size to offer; loops inside the body still offload. A condition that assigns, or that reads nothing the body writes, is refused at parse time.
- [x] ✅ [v0.6.0] Add support to efficient differentiation of fixed-point loops\
  The solve loop gets a fixed-point reverse in the tangent, the adjoint and the HVP, and a sequential loop that holds tape (a time loop) can be checkpointed with `checkpoint = true` (`stade_adjoint`, `stade_hvp`): the tape shrinks to about one segment, for one more forward run of each step.
